# 量潮沟通云实现方案

## 故事

看见水
迭代代号：T2 — 修河床
第一天
迭代计划会。会议室。
白板上贴着五张卡片。小林拿着马克笔，在每张卡片下面写了一个数字。
OP-01  雨水池72小时未搬运推送提醒          P1   2天
OP-03  标记共识时参与人<2弹出温和提示       P1   1天
OP-04  邮件退信后状态回退+推送              P0   3天
OP-02  单用户单日提交超10条消息折叠视图      P2   2天
OP-05  备忘14天无活动休眠图标               P3   0.5天
老张看着白板：”8.5天。我们一个迭代10个工作日。留1.5天buffer。刚好。“
小林摇头。
”OP-02不做了。“
阿美抬头看他。
”第18天赵磊那30条消息，后来他同事自己拖走了10条。用户自纠偏了。折叠视图是在替用户做判断。等再有第二个赵磊出现再说。“
阿美点头：”那省下来的2天给谁？“
小林在白板角落写了一行字：
Tech Debt
老张的保温杯放下了。
第二天
老张开始啃OP-04。邮件退信状态回退。
这是P0。第35天那封退信，让一个备忘卡在了”邮件已发送“的状态，但邮件实际上没送到。备忘没归档，也没回退。像一块石头卡在河道中间，水从两侧绕过去，但石头不动。
老张趴在工位上画状态机。
当前：
DRAFT_PENDING_REVIEW → SENT → (退信) → ???  ← 卡在这
目标：
DRAFT_PENDING_REVIEW → SENT → (退信) → SEND_FAILED → (用户修改邮箱) → DRAFT_PENDING_REVIEW → SENT
                                                    ↑
                                              回退到这里
他盯着那张图看了十分钟。
问题不是状态机画不出来。问题是——回退的时候，lineageChain怎么办？
那封退信已经发了。时间戳已经烙上了。如果状态回退，lineageChain里”邮件发送“这个节点是删掉还是保留？
删掉：历史就不完整了。两周后有人查，会发现”共识达成“直接跳到”归档“，中间缺了一环。
保留：那lineageChain里会出现两条邮件记录——一条失败的，一条成功的。像河里绕了一道弯。
老张去找小林。
小林想了三秒：”保留。“
”失败的也记？“
”记。河里每一块石头都留着，不管它挡没挡住水。“
老张回到工位，在lineageChain的数据结构里加了一个字段：
{
  stage: ”EMAIL“,
  ref: ”draft-001“,
  at: ”2026-09-30T09:01:00“,
  status: ”FAILED“,
  failureReason: ”BOUNCE“,
  retryOf: null
}
{
  stage: ”EMAIL“,
  ref: ”draft-002“,
  at: ”2026-10-02T14:00:00“,
  status: ”SENT“,
  retryOf: ”draft-001“
}
两条记录。第二条指向第一条。河绕了一道弯，但弯看得见。
第三天
阿美在切OP-05的UI。备忘休眠图标。
需求很简单：备忘14天没人动，右上角出现一个小月亮🌙。
她画了三个方案。
方案A：灰色月牙，静态的。安安静静挂在那儿。
方案B：月亮会”呼吸“——透明度从30%到50%缓慢渐变，像在打呼噜。
方案C：鼠标悬停时月亮转成一个小水滴，暗示”这条河睡着了，但水还在“。
她把三个方案贴在工位旁边，等路过的同事投票。
大刘路过，看了一眼，指了方案A。
”为什么？“
”B的动画会分散注意力。看板上如果有20张卡片，5张在呼吸，眼睛会往那儿飘。但休眠的备忘恰恰是你不该去关注的。它应该是安静的。安静到底。“
阿美想了一会儿，把方案B和方案C都删了。
方案A。灰色月牙。不动。
它在说：这条河睡着了。别管它。等它自己醒。
第四天
小林在写OP-01的逻辑。雨水池72小时未搬运推送提醒。
规则是：一条消息进入雨水池后，如果72小时内没有被AI搬运到任何备忘，系统给消息提交者推一个提醒。
”你的消息在雨水池里。“
小林在写推送文案的时候卡住了。
他写了三个版本：
版本1：”您3天前提交的消息尚未被整理，请关注。“
他读了一遍。像银行短信。删掉。
版本2：”雨水池有一条消息已等待72小时。是否需要手动归类？“
他又读了一遍。像系统在求他干活。删掉。
版本3：”你3天前丢了一块石头进雨水池。它还在那儿。“
他盯着这行字看了十秒。
这行字没有让用户做任何事。它只是告诉用户：你的石头还在。它没被搬走。可能是AI没找到它的同伴。也可能是它就是一块没有同伴的石头。
它不催促。不引导。不弹窗。不提供按钮。
它只是说了一句：我替你记着呢。
小林把版本3贴进了需求文档。
老张路过看了一眼：”这文案不像是产品写的。像写诗的。“
”产品本来就是写诗的。“小林说，”只不过诗变成了代码。“
第五天
老张把OP-04写完了。跑了一遍集成测试。
模拟流程：邮件发送 → SMTP返回退信 → 系统捕获退信事件 → 邮件状态回退为SENDFAILED → 备忘状态回退为CONSENSUSREACHED → 推送给标记人 → 标记人修改收件人邮箱 → 重新生成邮件草稿 → 重新发送 → 成功 → 归档。
lineageChain最终长这样：
MESSAGE  →  MEMO  →  CONSENSUS  →  EMAIL(FAILED)  →  EMAIL(SENT)  →  ARCHIVED
 09:17      02:03     14:23         09:01             14:00           14:05
                                    ↗ 退信            ↗ 重试
大刘验收的时候盯着这条链看了很久。
”两次EMAIL记录？“他问。
”对。一次失败，一次成功。“老张说。
”失败的那条也留？“
”留。“
”为什么不留？“
”因为它是真事。“
大刘在本子上写了：lineageChain保留失败路径。验收通过。
第六天
OP-03。标记共识时参与人<2弹出温和提示。
小林在画交互稿。弹窗内容：
”当前只有您一人参与讨论，是否仍要标记为共识？“
两个按钮：
仍要标记 （主按钮，蓝色）
先拉人讨论 （次按钮，灰色）
阿美看了稿子，皱了皱眉。
”次按钮的文案不对。“
”怎么了？“
”’先拉人讨论‘——这个文案像在教用户做事。但它本来该是用户自己的判断。“
小林想了想：”那改成什么？“
阿美在白板上写了一个词：”再想想“
小林看着这个词。
”再想想“不像一个按钮。它像一个朋友在你肩上拍了一下。它不告诉你该做什么。它只是让你停一秒。
两个按钮最终定为：
仍要标记
再想想
”再想想“点了之后弹窗关闭，什么都不发生。用户回到备忘卡片。他不一定要去拉人。他可能就是想自己标记。弹窗不阻拦他。它只是让他知道——系统看到了这一点。
第七天
小林在写OP-03的后端逻辑。判断条件很简单：
if consensus_marked and len(participants) < 2:
    trigger_prompt(”当前只有您一人参与讨论...“)
写着写着，他停下来。
他想起第25天阿美那次。她在自己跟自己讨论，然后自己标记了共识。前端组组长收到邮件，回了一句”谁拍的板“。
这个弹窗能解决那个问题吗？
不能。
因为阿美当时不是不知道参与人少。她只是觉得这个事情她自己就能定。弹窗弹出来，她会点”仍要标记“。问题不在于她不知道参与人少，问题在于邮件抄送逻辑把前端组拉了进来——一个没参与讨论的人被通知执行一个他没参与决策的事情。
弹窗治标。抄送逻辑治本。
但抄送逻辑在V1.0里已经上线了。改它意味着改邮件生成的核心规则。这不是一个P1小需求能覆盖的。
小林在笔记本上写了一行字，没有贴进本迭代：
T3候选：邮件抄送——只有参与过讨论（在discussion zone留过言）的人才会被自动填入收件人。标签推荐仅用于”建议抄送“，需用户逐个确认后加入。
他把这行字写在白板角落，用虚线框起来。虚线代表”下一个迭代可能讨论的事“。
老张路过，看到了那个虚线框。
”T3要砍什么？“
”不知道。到时候看哪个河床先塌。“
第八天
联调。
五个人围在一台显示器前。小林打开staging环境。
他从手机上丢了一条语音进雨水池。等AI聚类。打开备忘。自己跟自己讨论了一句。点了”标记共识“。
弹窗弹出来。
”当前只有您一人参与讨论，是否仍要标记为共识？“
[仍要标记]  [再想想]
小林点了”再想想“。弹窗关闭。回到备忘。他从右上角拉了一个人进来。那人在讨论区回了一句。参与人变成2。再次点”标记共识“。弹窗没弹。
共识标记成功。邮件草稿生成。
大刘在旁边记录：OP-03 弹窗逻辑验证通过。参与人≥2时不弹窗。参与人<2时弹窗。”再想想“按钮不阻塞。
然后模拟退信。老张手动把SMTP服务器配置成返回550错误。邮件发出。3秒后系统收到退信。邮件状态变为SENDFAILED。备忘回退到CONSENSUSREACHED。推送发出。
小林手机上收到一条通知：
”邮件发送失败：收件人邮箱地址不存在。备忘已回退至共识状态。点击修改收件人后重新发送。“
他点进去。修改了邮箱。重新生成草稿。发送。成功。
lineageChain里两条EMAIL记录。一条FAILED，一条SENT。
大刘记：OP-04 退信回退+重发验证通过。lineageChain保留失败路径。
最后验证OP-05。小林手动把一个备忘的最后活动时间改为15天前。刷新看板。卡片右上角出现一个灰色月牙。
不大。不闪。不动。就是一个小小的、安静的🌙。
阿美凑近看了看：”嗯。就是这个。“
第九天
回归测试。
大刘跑了一整天自动化测试。214条用例。210条通过。4条失败。
小林去看那4条失败用例。
第1条：极端情况——一条消息进入雨水池后，AI聚类的前一秒用户手动拖到了另一个备忘。两个操作并发。系统报了乐观锁异常。
老张看了一眼：”加个重试就行。AI扫描如果发现消息已经不是RAIN_DROP状态，跳过。“
10分钟改完。跑了一遍。通过。
第2条：邮件草稿生成时，备忘标签列表为空（用户手动删了所有标签）。AI推荐抄送时找不到依据，返回了空列表。前端没有处理空列表，抄送栏显示”undefined“。
阿美改了前端：空列表时抄送栏显示”无推荐抄送人“，并显示一个手动添加的输入框。
20分钟改完。通过。
第3条和第4条是同一个问题：移动端Safari在滑动看板时，卡片之间的拖拽响应有300ms延迟。这是Safari的老问题。
阿美说：”加 touch-action: pan-y 和 user-select: none。“
小林说：”这是Safari的坑。不是我们的坑。“
”但用户在Safari上用。用户不管是谁的坑。“
阿美改了CSS。通过。
214条。全绿。
第十天
迭代评审会。
会议室。窗帘拉着。投影仪亮着。
小林把白板上的五张卡片划掉了四张。剩下一张OP-02画了个叉。
”这个迭代做完了四件事。“他说。
他在白板上重新画了一条河。从左到右：雨水 → 备忘 → 共识 → 邮件 → 归档。
他在”雨水“和”备忘“之间画了一个小闸门，标上OP-01：72小时提醒。
他在”共识“那里画了一个小灯，标上OP-03：参与人提醒。
他在”邮件“那里画了一个弯，标上OP-04：退信回退。
他在”备忘“那里画了一个小月牙，标上OP-05：休眠。
然后他退后两步，看着这条河。
”上个月用户帮我们发现了四块塌了的河床。这个迭代我们补上了。“
他顿了一下。
”但T3还有一块没塌的河床。“他指着白板角落那个虚线框——邮件抄送逻辑改造。
”这个不急。等用户踩上去再说。“
老张端起保温杯。杯底磕了一下桌面。不是发令枪。是句号。
散会。
第十一天
小林一个人坐在空会议室里。
投影仪没关。河还亮着。
他在笔记本最后一页写了一行字。不是需求。不是数据。不是验收标准。
他写的是：
做产品像修河。你不可能一次把河床修完。水会告诉你哪里塌了。你要做的就是——听水。然后补那一块。补完再听。
有时候你会忍不住想挖一条新河。但新河里没有水。水在旧河里。在用户已经走过的那些弯路里。
别急。别抢着替水找路。水自己会找。
他合上笔记本。关了投影仪。
河暗了。但它还在流。
