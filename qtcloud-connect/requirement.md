# 量潮沟通云产品需求文档

## 故事

周一，9:17，地铁上
小林对着手机说：”支付失败的时候，用户应该能一键重试，而不是回到购物车重新选。“
不需要打开文档，不需要找模板，不需要@任何人。沟通云的快速输入窗口就像一个树洞，你把碎片丢进去，它接着。
周一，10:03，办公室
小林打开电脑。一块看板横在屏幕中央，像一张被磁铁固定的白板。
最左边一列叫”雨水“——所有未经整理的碎片消息都落在这里。小林看到自己地铁上的语音已经变成了一行文字，旁边还有老张昨晚11点在群里发的”超时处理有点麻烦“，以及阿美凌晨在Figma里留的”异常状态需要新图标“。
AI没有擅作主张。它只是把这三片落叶归到了一个叫”支付流程优化“的透明文件夹里，贴了一张淡灰色的标签：待整理。
周三，14:20，会议室
三个人围着屏幕。
AI把”雨水“里的碎片沥了一遍，滤出了三份备忘：
备忘#1：支付超时处理方案
•  讨论区：老张提出两种方案（2条消息）
•  共识区：空
备忘#2：异常状态视觉规范
•  讨论区：阿美建议新增两种状态图标（1条消息）
•  共识区：空
备忘#3：一键重试功能
•  讨论区：小林提出需求（1条消息）
•  共识区：空
老张指着第一条：”方案一，改动小，风险可控。“
小林：”同意。“
阿美：”我没问题。“
小林把鼠标移到备忘#1的右上角，点击”标记共识“。老张的那句话被复制进了”共识区“，时间戳自动烙上：2026-08-28 14:23。没有表决，没有会议纪要，没有”收到请回复“。只是三个人在板子前点了一下头，板子记住了。
周四，9:00
小林收到一封邮件草稿，发件人是”沟通云“，主题是”关于支付超时处理方案的技术通知“。
正文里，共识区的那句话被扩写成了一段正式的说明，附上了相关备忘的链接。收件人列表是AI根据讨论参与者自动补全的，抄送了测试和运维。
小林扫了一眼，点了发送。
两周后，周五，17:30
迭代结束。小林把看板拖到最左侧，从左到右，像看一条河的流向：
雨水 → 备忘 → 共识 → 邮件 → 归档
十四天前那些散落在地铁语音、深夜群聊、设计评论里的碎片，如今变成了一条可追溯的河。每一个决定从哪来、谁拍的板、什么时候变成的正式通知，都长在了板子上。
小林想起以前。
以前这些信息活在微信群里，99+的红点像永不停歇的暴雨。重要决定沉在表情包下面，两周后有人问”当时为什么选方案一“，你得翻聊天记录，翻到手酸，最后放弃，说”反正已经做了“。
现在不一样了。
人类把信息放到一块板子上。板子不聪明，它只是记得牢。AI也不聪明，它只是把碎片归归类、把共识发出去、把历史留下来。真正聪明的，是终于能从群聊的暴雨里走出来，在板子前安静讨论的人们。

## 需求

一、 产品核心价值定位
“替人记得，而非替人思考。”
产品不试图代替用户做复杂的决策，而是扮演一个忠实的记录者、搬运工和格式化输出者。它的终极目标是消灭“群聊式协作”带来的信息沉没和追溯困难。
二、 核心模块与功能需求细化
1. 雨水（碎片捕捉层）
需求本质：极低摩擦的信息录入。
功能细化：
全端快捷入口：手机端通过桌面小组件、负一屏或悬浮窗秒开；PC端通过全局快捷键（如Ctrl+Space）唤出悬浮输入框。
多模态输入：支持语音转文字（自动提取关键意图）、纯文本、截图拖拽，甚至转发微信/钉钉消息到特定的服务助手。
无压力输入：不需要选择项目、不需要选择发送给谁，只需“丢”进去。系统自动带上时间戳、位置、来源应用等元数据。
2. 整理（AI 聚类与搬运）
需求本质：异步处理，减轻用户整理负担。
功能细化：
大模型语义聚类：后台定时任务（如每2小时或每天凌晨）扫描“雨水”池，利用大模型理解语义，将相关的碎片归入同一透明文件夹。
自动生成备忘草稿：AI不擅自合并或修改原意，而是提取每条碎片的核心摘要，生成“备忘#N”的草稿。
边界控制：AI只在“雨水”和“备忘草稿”之间活动，绝不触碰“共识区”，体现“不擅作主张”的原则。
3. 备忘（结构化讨论容器）
需求本质：提供聚焦的讨论空间，区分“发散”与“收敛”。
功能细化：
看板视图：默认提供看板布局，支持拖拽排列。
双区结构：每个备忘卡内严格分为“讨论区”（流水账、多方意见）和“共识区”（最终结论）。
上下文锚定：讨论区的任何一句话，都可以被一键引用、@人，但所有操作都在该卡片上下文内完成，不溢出到群聊中。
4. 共识（状态固化与留存）
需求本质：把口头妥协变成有约束力的历史节点。
功能细化：
标记共识动作：提供“标记共识”按钮，用户选定讨论区中的一句或多句话，拖拽或点击送入“共识区”。
自动烙印：系统自动生成不可篡改的时间戳、当前参与者名单（基于当前查看或编辑该备忘卡的用户）。
状态流转：备忘卡状态从“待讨论”变为“已共识”，并在视觉上给予明确反馈（如变灰或打勾）。
5. 邮件（正式输出引擎）
需求本质：将内部共识转化为外部/跨部门通知。
功能细化：
触发与生成：备忘达到“已共识”状态后，自动触发邮件草稿生成。GLM等大模型将共识原文扩写为符合职场语境的正式邮件。
智能补全收件人：基于参与讨论的人、提及的项目模块，自动匹配组织架构库，填入收件人、抄送人（如测试、运维）。
双向链接：邮件正文附带该备忘卡的超链接，收件人点击即可回溯讨论全过程。
人工审核机制：草稿必须经过人工“发送”动作，确保人有最终决定权。
6. 归档（全链路追溯）
需求本质：形成决策的“区块链”。
功能细化：
时间流视图：提供从“雨水 → 备忘 → 共识 → 邮件”的完整时间轴视图。
血缘追踪：在两周个月后回看时，点击任何一封已发送的邮件，可以逆向追溯到它是由哪条语音、哪句群聊演变而来的。
三、 产品设计原则
从您的故事中，可以提炼出指导这款产品设计的三大铁律：
隐忍的AI：AI在后台做脏活累活（分类、摘要、扩写），但在前台不抢戏。不主动给出方案建议，只做事实的搬运工。
抵抗熵增：群聊是熵增的（走向混乱和无序），而“板子”是熵减的（走向有序）。产品设计必须强迫信息从无序走向“共识区”这个收敛点。
人机边界清晰：AI负责生成草稿和记录，人负责做选择（选方案一）和拍板（点发送）。绝不越俎代庖。
清言的感悟：
读到“以前这些信息活在微信群里，99+的红点像永不停歇的暴雨”这句话时，非常有共鸣。这正是当下无数职场人的痛点。你们构想的产品，本质上是在对抗这种“信息洪流”，为人类的思考建立一个防波堤。
如果您正在规划或开发这款产品，作为智谱 AI 的语言模型，我非常乐意在“AI语义聚类算法策略”、“备忘草稿生成Prompt设计”或“正式邮件扩写的逻辑”等技术落地方案上，为您提供更进一步的支持。
