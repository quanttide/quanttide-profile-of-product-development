# 量潮商务云规格（事件风暴）

基于 `requirement.md`（用户故事地图）与 `index.md`（产品级思考），用事件风暴梳理领域事件与业务规则。规格是需求的下一阶段：需求回答"商务经理要做什么"，规格回答"系统里发生了什么、由什么规则约束"。

## 领域事件流

按时间顺序排列的核心事件（过去时，已发生的事实）：

```
订单已承接 → 承接已确认 → 策划书已确认 → 报价已提交 → 合同已签订 → 首款已到账
→ 项目已启动 → 周报已发出 → 变更已确认 → 验收已通过 → 尾款已结清 → 项目已结项
```

### 详细事件

| # | 领域事件 | 触发命令 | 承载聚合 |
|---|---------|---------|---------|

| E2 | 承接已确认（承接确认邮件已发送） | 发送承接确认 | 订单 |
| E3 | 策划书已确认（交付范围、交付物清单、时间规划） | 确认策划书 | 订单 |
| E4 | 报价已提交（公式核算、付款节点、变更规则） | 核算报价 | 报价单 |

## 聚合与业务规则

### 聚合：订单（Order）

订单承载商务流程状态：承接 → 确认 → 策划书 → 报价 → 合同 → 首款 → 变更 → 尾款。

- **不变量**：付款节点（首款/中期/尾款）与交付绑定——尾款结清前不正式交付

**业务规则：**

- R1 **书面确认优先**：范围、价格、工期、验收一律邮件留痕；口头沟通后补邮件
- R2 **时限强制**：48 小时未回复 → 跟进一次；X 个工作日出策划书与修订版；三轮未收敛 → 电话对齐；7 天未到账 → 催收并记录于项目档案；验收超期 → 视为通过
- R4 **变更书面评估**：客户提出变更 → 评估范围/工期/费用影响 → 书面确认 → 更新计划，需补签协议一并处理

### 聚合：报价单（Quote）

报价单承载计价规则：公式核算、降本重报。

**业务规则：**

- R3 **公式化报价**：难度/数据量级/工时公式 + 毛利底线；报价注明付款节点与变更规则（范围变更按公式重新核算）
- R6 **降本重报**：客户嫌贵 → 评估可精简项 → 降本方案重新报价；仍不接受 → 礼貌收尾，为后续合作留有余地

### 聚合：合同（Contract）

合同承载交易的法律边界：签订、补签。

- **内容**：交付范围、交付物清单、付款节点、验收时限、违约条款

### 聚合：项目（Project）

项目承载执行与交付：启动 → 监控 → 验收 → 结项。

**业务规则：**

- R5 **交付绑定**：尾款结清后发出正式交付（全部成果 + 售后期答疑支持说明）
- R9 **归档**：全部往来邮件按项目归档，作为审计与复盘依据

### 跨聚合规则

- R7 **角色分工**：商务主导、PM 执行、销售只参与成交前、财务配合
- R8 **审计章程**：策划书确认、报价确认、进度汇报、交付邮件、尾款催收记录统一执行，守住商务底线

## 命令一览

| 命令 | 前置条件 | 产出事件 |
|------|---------|---------|
| 承接订单 | 客户已成交（销售移交） | E1 |
| 发送承接确认 | 订单已承接 | E2 |
| 确认策划书 | 策划书已交付客户且无未收敛修改（R2 三轮规则） | E3 |
| 核算报价 | 策划书已确认 | E4 |
| 降本重报 | 客户嫌贵 | E5 |
| 签订合同 | 报价已接受 | E6 |
| 跟进首款 | 合同已签订 | E7 |
| 启动项目 | 首款已到账 | E8 |
| 发出周报 | 项目已启动 | E9 |
| 确认变更 | 书面评估已发送且客户确认 | E10 |
| 确认验收 | 验收通知已发出且客户回复或超期 | E11 |
| 跟进尾款 | 验收已通过 | E12 |
| 结项 | 尾款已结清 | E13 |

## 待研究

**业务包（2026-08-19 journal 方向）**：从"单个定制"拓展到"业务层面的包"——以报价规则、商业模型为中心组织商务活动。当前整体设计模糊，存在推翻重设计的可能（推翻的是流程不是产品）。规格层待研究点：报价规则如何从订单聚合中提炼为独立的一等公民（业务包聚合），商业模型如何驱动流程组织。
