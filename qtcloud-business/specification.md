# 量潮商务云规格（事件风暴）

基于 `requirement.md`（用户故事地图）与 `index.md`（产品级思考），用事件风暴梳理领域事件与业务规则。规格是需求的下一阶段：需求回答"商务经理要做什么"，规格回答"系统里发生了什么、由什么规则约束"。

## 领域事件流

按时间顺序排列的核心事件（过去时，已发生的事实）：

```
业务已定义 → 订单已承接 → 承接已确认 → 策划书已确认 → 报价已提交 → 合同已签订 → 首款已到账
→ 项目已启动 → 周报已发出 → 变更已确认 → 验收已通过 → 尾款已结清 → 项目已结项 → 业务已校准
```

## 聚合与业务规则

### 聚合：业务（Business）

业务是商务活动的组织中心：承载报价规则、商业模型、毛利底线与模板。订单是业务的实例——订单引用所属业务，继承其报价规则、付款节点与变更规则。

- **不变量**：业务定义先于订单承接（无业务则无订单）；报价公式参数 + 毛利底线构成业务边界

**业务规则：**

- R0 **业务定义先行**：承接订单前，所属业务必须已定义（报价规则、商业模型、毛利底线、模板）
- R10 **订单引用业务**：每个订单标注所属业务，报价/变更/模板从业务继承；订单执行数据回流校准业务参数（E14）

### 聚合：订单（Order）

订单承载商务流程状态：承接 → 确认 → 策划书 → 报价 → 合同 → 首款 → 变更 → 尾款。

- **不变量**：付款节点（首款/中期/尾款）与交付绑定——尾款结清前不正式交付

**业务规则：**

- R1 **书面确认优先**：范围、价格、工期、验收一律邮件留痕；口头沟通后补邮件
- R2 **时限强制**：48 小时未回复 → 跟进一次；X 个工作日出策划书与修订版；三轮未收敛 → 电话对齐；7 天未到账 → 催收并记录于订单档案；验收超期 → 视为通过
- R4 **变更书面评估**：客户提出变更 → 按所属业务规则评估范围/工期/费用影响 → 书面确认 → 更新计划，需补签协议一并处理

### 聚合：合同（Contract）

合同承载交易的法律边界：签订、补签。

- **内容**：交付范围、交付物清单、付款节点、验收时限、违约条款

### 聚合：项目（Project）

项目承载执行与交付：启动 → 监控 → 验收 → 结项。

**业务规则：**

- R5 **交付绑定**：尾款结清后发出正式交付（全部成果 + 售后期答疑支持说明）
- R9 **归档**：全部往来邮件按订单归档，作为审计与复盘依据

### 跨聚合规则

- R7 **角色分工**：商务主导、PM 执行、销售只参与成交前、财务配合
- R8 **审计章程**：策划书确认、报价确认、进度汇报、交付邮件、尾款催收记录统一执行，守住商务底线

## 读模型（查询展示）

| 读模型 | 内容 | 支撑聚合 |
|--------|------|---------|
| 业务视图 | 各业务的报价规则、商业模型、毛利底线、订单量 | 业务 |
| 订单档案 | 全部往来邮件与审计记录（可追溯） | 订单/项目 |

| 经营偏差 | 订单执行数据 vs 业务报价规则（实际工时/毛利/回款周期） | 业务 |

## 命令一览

| 命令 | 前置条件 | 产出事件 |
|------|---------|---------|
| 定义业务 | — | E0 |
| 校准业务 | 订单执行数据已积累 | E14 |
| 承接订单 | 所属业务已定义（R0） | E1 |
| 发送承接确认 | 订单已承接 | E2 |
| 确认策划书 | 策划书已交付客户且无未收敛修改（R2 三轮规则） | E3 |
| 核算报价 | 策划书已确认、所属业务已定义 | E4 |
| 降本重报 | 客户嫌贵 | E5 |
| 签订合同 | 报价已接受 | E6 |
| 跟进首款 | 合同已签订 | E7 |
| 启动项目 | 首款已到账 | E8 |
| 发出周报 | 项目已启动 | E9 |
| 确认变更 | 按业务规则书面评估已发送且客户确认 | E10 |
| 确认验收 | 验收通知已发出且客户回复或超期 | E11 |
| 跟进尾款 | 验收已通过 | E12 |
| 结项 | 尾款已结清 | E13 |
