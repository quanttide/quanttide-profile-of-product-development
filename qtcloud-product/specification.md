# 量潮产品云事件风暴

基于 `requirement.md`（用户故事地图）与 `index.md`（产品级思考），用事件风暴梳理领域事件与业务规则。规格是需求的下一阶段：需求回答"用户要什么"，规格回答"系统里发生了什么、由什么规则约束"。

## 领域事件流

按时间顺序排列的核心事件（过去时，已发生的事实）：

```
产品已登记 → 素材已提交 → 地图草稿已生成 → 草稿已修订 → 地图已评审 → 地图已定稿 → 地图已进入下一阶段
```

### 详细事件

| # | 领域事件 | 触发命令 | 承载聚合 |
|---|---------|---------|---------|
| E1 | 产品已登记（名称、状态、负责人） | 登记产品 | 产品 |
| E2 | 产品已切换 | 切换产品 | 产品 |
| E3 | 素材已提交（访谈记录、需求文档、功能清单） | 提交素材 | 故事地图 |
| E4 | 地图草稿已生成（AI 从素材生成） | 生成草稿 | 故事地图 |
| E5 | 草稿已修订（标记非用户视角内容重新生成、合并过细/过粗卡片） | 修订草稿 | 故事地图 |
| E6 | 地图已评审（校验视角一致性、格式） | 评审地图 | 故事地图 |
| E7 | 地图已定稿（确认格式无误） | 定稿地图 | 故事地图 |
| E8 | 地图已进入下一阶段（规格/迭代/验收/运营） | 流转阶段 | 产品 |

## 聚合与业务规则

### 聚合：产品（Product）

产品是体系的元结构单元，承载产品清单与跨产品关系。

- **状态**：登记中 → 需求中 → 规格中 → 迭代中 → 运营中（随阶段流转）
- **不变量**：产品名称唯一；负责人必填

**业务规则：**

- R1 产品边界先于产品内部知识——登记产品（划清边界）先于梳理需求（产品边界活动在需求活动之前）
- R2 产品与产品之间的关系由产品体系元结构管理（跨系统边界优先于产品内部领域知识）

### 聚合：故事地图（Story Map）

故事地图是需求阶段的中心聚合，三层结构（活动/任务/故事卡）承载需求内容。

- **状态**：草稿 → 修订中 → 已评审 → 已定稿
- **不变量**：三层结构完整（活动/任务/故事卡）；每条故事为"用户要…"句式

**业务规则：**

- R3 **AI 产出必过人审**：AI 生成的地图草稿必须经人工评审后才能定稿——草稿不是最终需求
- R4 **视角一致性**：所有故事必须符合目标用户视角；AI 输出中不符合用户视角的内容必须被标记并重新生成（"功能清单化"是典型不合格形态）
- R5 **颗粒度一致性**：故事卡颗粒度必须一致，一条故事 = 一个可独立交付的用户价值；过细或过粗的卡片必须合并/拆分
- R6 **素材可追溯**：每条故事可回溯到素材来源，无凭空添加
- R7 **画像先行**：梳理前必须先确定用户画像（素材确认或与人类讨论），它是审视素材的视角
- R8 **明确性检验**：能做出规格、写得出用户故事即明确，写不出来即模糊——模糊的需求不得进入下一阶段
- R9 **阶段流转是检验**：需求在阶段间能否顺畅推进，本身就是明确性最好的检验

## 读模型（查询展示）

| 读模型 | 内容 | 支撑聚合 |
|--------|------|---------|
| 产品清单 | 所有产品的概览（名称、状态、负责人），快速定位与切换 | 产品 |
| 地图画布 | 用户故事地图三层结构可视化，可拖拽重组 | 故事地图 |
| 组合视图 | 跨产品成熟度、投入分布、版本时间线（支撑体系整体决策） | 产品 |

## 命令一览

| 命令 | 前置条件 | 产出事件 |
|------|---------|---------|
| 登记产品 | 名称唯一、负责人已指定 | E1 |
| 切换产品 | 产品已登记 | E2 |
| 提交素材 | 素材为原始零碎话语（日志/访谈/文档） | E3 |
| 生成草稿 | 素材已提交、画像已确定（R7） | E4 |
| 修订草稿 | 草稿已生成 | E5 |
| 评审地图 | 草稿已修订 | E6 |
| 定稿地图 | 已通过评审（R3/R4/R5） | E7 |
| 流转阶段 | 地图已定稿 | E8 |
