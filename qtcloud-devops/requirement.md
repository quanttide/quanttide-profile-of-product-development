# 量潮 DevOps 云用户故事地图

用户画像：需要集中发布信息、观测整个系统迭代进展的 DevOps 负责人（平台管理员等内部角色）。

## 活动：信息集中

先把 GitHub 仓库同步到 GitLink，只做「已读」，把各种发布信息集中到 DevOps。

### 任务：仓库同步

· 用户要把 GitHub 仓库同步到 GitLink，作为信息集中的基础
· 用户要只以「已读」的方式接收信息（先只做已读，不做更多处理）

### 任务：发布信息集中

· 用户要把各种发布信息集中到 DevOps，减少去中心化模式下看不到信息的问题
· 用户要能看到各 scope 的更新信息

## 活动：事件申报

服务端本质是缓存，构成基本的事件申报工作流。

### 任务：缓存式服务端

· 用户要在仓库有更新时拉取并整理各 scope 的更新信息
· 用户要在仓库没有更新时直接返回数据库中的数据

## 活动：迭代观测

仓库足够多、关系变复杂时，引入观测工具看到整个系统的迭代进展。

### 任务：观测进展

· 用户要看到整个系统的迭代进展
· 用户要观测部署结果与发布状态，作为验收依据

## 活动：命令行观测改造

命令行逐步改造，让它具备观测功能。

### 任务：云端接通

· 用户要把 `status` 这类信息与云端接通
· 用户要让命令行与本地仓库进行一定程度的同步
· 用户要明确本地与仓库以谁为事实源（尚未明确）

## 活动：发布管理

### 任务：发布流程

· 用户要基于子模块状态自动生成 Release（标签、CHANGELOG、Docker 镜像）
· 用户要在发布前自动校验（预检不通过则阻止发布）
