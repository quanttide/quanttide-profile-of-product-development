# QtCloud DevOps（量潮 DevOps 云）

## 定位

- 量潮云的 DevOps 后台：承接部署结果的验收与观测，不追求替代 CI 触发的部署链路——在自己系统稳定之前直接参与部署意义不大
- 观测与信息集中中心：先把 GitHub 仓库同步到 GitLink，只做「已读」，把各种发布信息集中到 DevOps，极大减少去中心化模式下看不到信息的问题
- 当仓库足够多、关系变复杂时，它是观测整个系统迭代进展的工具

## 核心目标

- 让部署与发布可观测：先做部署状态、把发布信息集中起来，让整个系统的迭代进展可见
- 构成基本的事件申报工作流，减少去中心化模式下信息不可见的问题

## 阶段方法

- 已读先行：先把 GitHub 仓库同步到 GitLink，只做「已读」功能，把各种发布信息集中起来
- 缓存式服务端：服务端本质是缓存——仓库有更新就拉取并整理各 scope 的更新信息，没有更新就直接返回数据库数据
- 观测优先：相对命令行更多是端测工具，服务端与客户端最新功能多往观测上走；命令行逐步改造，把 `status` 这类信息与云端接通、与本地仓库保持一定程度的同步
- 不提前设计状态机：早期设计失败是因为不知道状态机在整个地图中的功能是什么，贸然接入可能定义了状态却跟全局没关系、根本启用不了

## 数据驱动

- 服务端即缓存：数据由仓库更新驱动，有更新就拉取整理，无更新直接返回数据库数据
- 用各 scope 的更新信息与发布信息观测整个系统的迭代进展，指导功能走向

## 需求与 AI

- 不能过早设计状态机：先弄清楚状态在整个地图中的功能是什么，再决定是否接入，否则定义了状态却与全局无关，根本无法启用
- 待解决：本地与仓库之间以谁为事实源的问题，需要先能同步成，才能继续深入
