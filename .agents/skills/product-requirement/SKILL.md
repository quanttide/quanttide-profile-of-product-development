# 用户故事地图撰写技能

## 目标

撰写一份可信赖的产品用户故事地图：以用户视角刻画产品需求，让所有人看到同一张产品地图。

## 流程

### 第一步：确定用户画像

一行完成：`用户画像：需要…的[角色]`

### 第二步：划分活动（用户旅程阶段）

按用户行为的时间顺序划分活动（不是系统模块）。

每个活动包含：
- **活动名**：`## 活动：[阶段名]`
- **活动描述**：一段话说明这个阶段的流程、目标、价值
- **任务列表**：活动内的具体动作

### 第三步：梳理任务

任务 = `### 任务：[动词+名词]`

任务描述活动内的具体动作，用一句话概括（不展开细节）。

### 第四步：展开故事

故事 = 每条以"用户要…"开头，展开任务的具体细节：

```
· 用户要[动作]，[目的/价值]
```

一个任务下可以有多个故事（任务是概括，故事是细节）。

故事颗粒度标准：**一条故事 = 一个可独立交付的用户价值**（不是系统功能点，也不是太大的"管理整个XX"）。

### 第五步：评审校验

逐条检查（见验收标准），修正不合格的故事。

## 验收标准

### 必须满足

- [ ] 每个活动都有描述段（一段话说明流程/目标/价值）
- [ ] 所有故事都是"用户要…"句式（无系统动作混入）
- [ ] 活动按用户旅程时间顺序排列（不是系统架构顺序）
- [ ] 主线故事清晰——用户读完能理解"这个产品帮用户解决了什么问题"
- [ ] 所有故事符合目标用户视角（不是开发者/系统视角）

### 质量检查

- [ ] 故事颗粒度一致（一条故事 = 一个可独立交付的用户价值）
- [ ] 没有功能清单式描述（"支持XX"不是故事）
- [ ] 用户画像一行完成（角色 + 需求）

### 反模式（避免）

| 问题 | 示例 | 修正 |
|------|------|------|
| 系统动作 | "系统要记录部署状态" | "用户要记录部署状态…" |
| 功能清单 | "支持多租户" | "用户要按租户隔离数据…" |
| 模块当活动 | "活动：认证模块" | "活动：用户登录" |
| 缺描述段 | 直接列任务 | 先写活动流程说明 |
| 颗粒度过大 | "用户要管理整个系统" | 拆成具体动作 |
| 颗粒度过细 | "用户要点击保存按钮" | 合并为"用户要保存…" |

## 优先级标注

故事地图**不标注优先级**（P0/P1/P2）。原因：
- 故事地图的目标是**刻画需求**（是什么），不是规划版本（先做什么）
- 优先级在版本规划阶段确定（活动三：迭代），不应在需求阶段混入
- 避免"标注了 P0 就不做 P1"的思维定式——需求完整比优先级标注更重要

## 示例：量潮产品云（QtCloud Product）

用户画像：需要统筹规划产品研发节奏的产研负责人。

### 活动：需求

产研负责人先登记产品，然后利用 AI 辅助梳理出一版用户故事地图，再以评审视角校验地图质量，修正 AI 可能出现的"功能清单化"问题，最终得到一份可信赖的需求地图。

**任务：管理产品清单**

· 用户要登记一个新产品，写明名称、状态、负责人
· 用户要在多个产品间切换，分别管理不同产品

**任务：梳理用户故事地图**

· 用户要把已有素材交给 AI，生成初始用户故事地图草稿
· 用户要让 AI 把系统功能描述改写成"用户要…"的句式
· 用户要让 AI 按用户旅程时间顺序组织故事
· 用户要在一块画布上看到用户故事地图的三层结构（活动/任务/故事卡）
· 用户要能编辑、合并、拆分 AI 生成的故事卡片

**任务：评审用户故事地图**

· 用户要能区分 AI 建议的故事和手动确认的故事
· 用户要检查地图中的故事是否都是"用户要…"的句式
· 用户要确认每个活动下的任务是否按用户旅程顺序排列

### 活动：规格

**任务：事件风暴**

· 用户要用事件风暴的方式梳理领域事件和业务规则

### 活动：迭代

**任务：组合决策**

· 用户要查看跨产品的组合视图（成熟度、投入分布、版本时间线）
· 用户要管理产品之间的关系，支撑产品体系的整体决策

### 活动：验收

**任务：用例管理**

· 用户要管理验收用例，验证产品是否满足需求

### 活动：运营

**任务：数据驱动**

· 用户要收集实际运营数据，发现合适的产品管理结构
